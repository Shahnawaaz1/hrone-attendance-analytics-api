# DECISIONS.md

1. **Indexes.** I created a unique index on `emp_code` in the `employees` collection to guarantee uniqueness per R1. I also created a unique compound index on `(emp_code, date)` in `attendance_logs` to prevent duplicate check-ins for the same day. I considered adding indexes on `department`, but rejected it as the `employees` dataset size is presumably small enough compared to attendance logs, and we don't query it frequently enough to offset the insert penalty. I also created an index on `(date, emp_code)` to serve the `attendance_list` queries optimally without in-memory sorting.
2. **Punch-in race.** Both requests attempt to insert a new document with the same `(emp_code, date)` pair concurrently. Due to the unique compound index, the first one succeeds (returns 201). The second one throws a `DuplicateKeyError` at the database level, which the application catches and correctly translates into an HTTP 409 response.
3. **Ties.** It returns both employees tied at the same rank. Since the `limit` filter is applied *after* `$setWindowFields` rank generation, if the cutoff is at rank 10 and three employees share rank 10, the API returns 12 items.
4. **Headcount.** The aggregation pipeline starts from the `employees` collection rather than `attendance_logs`. It matches all employees active up to the cutoff date, and then uses a `$lookup` to join their attendance logs. This ensures zero-log employees are still grouped and counted towards the headcount.
5. **One thing you would change.** If data grew 100x, I would implement materialized views or pre-aggregated bucket collections for the analytics endpoints rather than aggregating millions of logs on-the-fly.
